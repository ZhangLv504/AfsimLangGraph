# 阶段 3：错误驱动的定向修复

## 目标

- 编译前拦截缺定义的 `platform_type`，省一次 `mission.exe` 运行。
- 把 mission 报错映射到 `errors-ref` / lesson 语料，命中片段注入下一轮提示词。
- 失败后只改相关文件，而不是整份重生成。
- 每轮留痕记录修复模式、检索关键词与命中的教训。

## 改动

### 静态引用检查

新增 [afsim_lg/afsim/statics.py](../afsim_lg/afsim/statics.py)：

- `check_platform_types(files)`：`platform <实例> <类型>` 的类型必须在文件集内有 `platform_type` 定义；`WSF_` 前缀视为内置类型放行。
- **只查存在性，不查定义顺序**：探针实测 AFSIM 2.9 允许 `platform` 写在 `platform_type` 之前（两遍解析），最初设想的“先定义后使用”会误报。
- 跳过 `/* */`、整行 `#`/`//` 注释和 `script`/`execute` 区域；块内 `platform <名称>` 引用只有两个 token，不参与检查。
- **不做 `end_` 闭合检查**：demos 里 `platform`/`sensor`/`processor` 既可能是定义块，也可能是块内引用（如 `processor track_manager`、`platform blue_airlifter_jet`），词法栈在 demos 上造成数百个文件误报。闭合错误交给 mission 报 `Unknown command` 后走教训检索。

接入 `validate`：

- 静态检查失败写 `attempts/attempt-NN/static.json`，跳过 `mission.exe`，`mission.exit_code = -2`、`static_failed = true`。
- `assess` 的修复建议对应改为“先修复静态检查错误”。

### 报错关键字检索

新增 [afsim_lg/rag/errors.py](../afsim_lg/rag/errors.py)：

- `extract_error_keywords(errors)`：覆盖 `Unknown command: X`、`Could not find platform_type X`、`X not closed`、`Undefined X`、`Unable to open ...`、`Unknown weapon/sensor/platform/type`、`Invalid ... format`；去掉 `@ 'file', line N` 位置后缀；最多 8 个关键词。
- `search_error_refs(keywords)`：用 Chroma `where_document` 做字面检索，只扫 `kind = ref / lesson`；每个关键词每类最多 2 条、总数 4 条，先 ref 后 lesson。
- `Undefined X` 规则是真实端到端暴露后补的：第一版只覆盖 `Unknown command`，`Undefined radar_signature` 检索为空。

### 定向修复

- `MainState` 新增 `generation_mode`、`error_keywords`、`error_refs`。
- `generate`：有上一轮 `files` 与 `feedback` 时走 `REPAIR_SYSTEM`，只要求输出需要修改的文件；解析不到文件时在同一节点内回退整份生成。
- 合并策略：只覆盖模型返回的文件，未返回的文件沿用上一轮。
- `fix`：检索结果写 `attempts/attempt-NN/fix.json`（feedback、keywords、hits），反馈文案区分“静态检查错误”和“mission.exe 报错”。
- `summary.json`、`manifest.json`（经 attempts）与 CLI 汇总都带 `generation_mode`。

## 验证

- 单元测试：28 passed。新增静态检查 4 项、报错提取/检索 4 项、修复模式与回退 2 项、validate 静态短路 1 项。
- 探针：
  - `platform` 先于 `platform_type` 定义：可正常加载并启动仿真。
  - 缺类型：`ERROR: Could not find platform_type FOO @ 'main.txt', line 1, near column 16`。
  - sensor 未闭合：在 `end_platform_type` 处报 `ERROR: Unknown command: end_platform_type`。
- 真实端到端（`workspace/runs/stage3-e2e2`，需求：蓝方一架飞机 12000 m 平飞 90 s，无交战）：
  - 第 1 轮 full：mission 报 `ERROR: Undefined radar_signature.`。
  - fix 提取 `['Undefined radar_signature', 'radar_signature']`，命中 `refs/complete-ref.md` 两条、lesson 索引、`[L011] 混淆 sensor 和 radar_signature`。
  - 第 2 轮 repair：只改 `main.txt`（补 `radar_signature FIGHTER_RADAR_SIGNATURE WSF_RADAR_SIGNATURE` 定义，高度改成 `12000 m`），mission 退出码 0，确定性检查全部通过，验收 passed。
  - manifest：`generations=2`，attempt-01 `full`、attempt-02 `repair`。
- 对照：补 `Undefined` 规则前的 `workspace/runs/stage3-e2e` 同样需求两轮均失败；第二轮虽进入 repair，但 `keywords=[]`、文件无改动。补规则后同一需求通过。

## 已知边界

- 静态检查不解析 `include` 的外部定义文件，只认生成文件集；使用外部定义的非 `WSF_` 类型会误报。
- 没有块闭合静态检查（原因见上），未闭合块仍要跑 mission 才能发现。
- 修复是文件级完整替换，7B 模型写不出可靠的块级 diff；单文件展示上限 3000 字符，超长文件可能看不到错误位置。
- 关键词是字面规则，中文验收反馈不触发检索；宽泛词（如 `Unknown command`）会占用命中名额。
- 修复轮沿用首轮检索到的技能语料，只额外检索 ref/lesson，没有按错误重新检索技能语料。
- `架构.md` 由用户维护，本阶段未改。
