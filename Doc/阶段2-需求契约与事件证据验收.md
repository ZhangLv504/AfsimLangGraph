# 阶段 2：需求契约与事件证据验收

- 日期：2026-11-15
- 对应提交：`e366d2e 实现需求契约、事件证据验收与每轮留痕`

## 目标

把“怎么算通过”从模型主观判断改成可复现的检查：需求先结构化，验收读 `mission.exe` 实际产生的事件，失败原因和每轮证据都能回看。

## 需求契约

新增 [afsim_lg/contract.py](../afsim_lg/contract.py)：

| 模型 | 字段 |
|---|---|
| `PlatformSpec` | `side`、`domain`、`count`、`main_entity`、`sensors`、`weapons` |
| `Expectation` | `kind`（detect / fire / hit / kill）、`actor_side`、`target_side`、`min_count` |
| `ScenarioContract` | `summary`、`duration_sec`、`platforms`、`expectations`、`notes` |

- 解析节点 `parse_requirement` 位于图首，调用模型以 JSON 模式输出契约，Pydantic v2 校验；失败时带错误重试一次，再失败则降级：时长用正则从需求里猜（秒/分钟/小时），平台与事件留空，错误写入 `contract_error.txt`。
- 中文字段自动归一化：`蓝方→blue`、`探测→detect`；`sensors/weapons` 只允许填需求明确提到的装备，避免给飞机自动补雷达和导弹。
- 契约写入 `workspace/runs/<run_id>/contract.json`，同时进入状态与 manifest。

## 事件证据

新增 [afsim_lg/afsim/evt.py](../afsim_lg/afsim/evt.py)，基于真实官方 demo 实测的 evt 格式：

- 时间戳有两种：`300.00000`（秒）与 `00:02:10.0`（h:m:s），解析器都支持。
- 长消息以行尾 `\` 续行，解析前先按续行合并。
- 关键事件：`PLATFORM_ADDED`（提供平台名→阵营映射）、`SENSOR_TRACK_INITIATED`（探测）、`WEAPON_FIRED`、`WEAPON_HIT`（`Result: KILLED` 计为毁伤）、`PLATFORM_BROKEN`。
- 探测按 `(传感器平台, 目标)` 去重，毁伤按被毁平台去重。

契约要求事件时，若生成文件里完全没有 `event_output`，写盘节点会追加一段标准事件输出（`enable PLATFORM_ADDED / SENSOR_TRACK_INITIATED / WEAPON_FIRED / WEAPON_HIT / PLATFORM_BROKEN`），输出到 `output/events.evt`。实测不开 `PLATFORM_ADDED` 时事件里没有阵营，无法按阵营验收，因此该事件是必需项。

## 确定性检查

新增 [afsim_lg/graph/checks.py](../afsim_lg/graph/checks.py)，逐项输出 `{name, ok, detail}`：

| 检查 | 依据 |
|---|---|
| 仿真时长 | 工程内 `end_time` 换算成秒，不小于契约要求 |
| 阵营覆盖 | 契约要求的阵营都出现在 `side` 声明中 |
| 平台数量 | `platform <实例>` 数量不少于契约总平台数 |
| 事件:<kind> | evt 中按阵营过滤后的事件数达到 `min_count`；缺 evt 直接失败 |

验收结论：`passed = 所有确定性检查通过 && 验收模型通过`。验收模型只处理检查未覆盖的语义项，提示词明确要求：检查失败必须判 false、不得虚构需求没写的平台/装备/交战、契约 expectations 为空时不得因“没有交战”判失败。

## 每轮留痕

```text
workspace/runs/<run_id>/
├─ contract.json              需求契约
├─ contract_error.txt         契约解析失败原因（如有）
├─ manifest.json              汇总：需求、契约、状态、生成轮数、各轮摘要
└─ attempts/attempt-NN/
   ├─ main.txt / setup.txt   本轮生成文件（系统注入 event_output 后的版本）
   ├─ retrieved.json         本轮检索命中的完整片段、路径、距离
   ├─ mission.json           mission.exe 摘要
   ├─ mission_stdout.log     完整输出
   ├─ checks.json            确定性检查明细
   ├─ evidence.json          事件统计
   ├─ assessment.json        验收结论
   └─ summary.json           本轮汇总
```

- 检索目前只在首轮做一次，各轮 `retrieved.json` 内容相同，等下一阶段做按错误重检索后才会分化。
- 生成轮数改为由 `generation` 字段单独计数；此前用 `attempt + 1`，失败重试时会多算一轮（实测出现过 `generations=3` 而实际只生成 2 次）。

## 验证

- 测试：17 passed，新增契约归一化/降级、evt 解析、确定性检查、event_output 注入、真实探测证据链（真实 `mission.exe`）。
- 手工探测场景（红方雷达 + 蓝方飞机，120 s）：evt 在 0 s 产生 `SENSOR_TRACK_INITIATED`，四项检查全部 PASS。
- 简单需求端到端：契约 `duration_sec=90`、无交战要求，生成一次通过；确定性检查 3 项全 PASS，验收通过。
- 调参记录：旧验收提示词曾把“无交战需求”判成“交战事件未发生”，收紧规则后通过；契约曾给飞机虚构雷达/导弹，增加约束后 `sensors/weapons` 为空。
- 探测需求端到端：7B 两轮生成均无法编译（先是未定义 `platform_type`，后是 `Unknown command: run`），说明**验收与留痕链路可用，生成质量仍是短板**。

## 已知边界

- 若模型自带 `event_output` 但缺少 `PLATFORM_ADDED` 等 enable，事件里没有阵营，按阵营的事件检查会判 0；目前只做“缺失时注入”，不做“已有但补全”。
- 契约的 `domain` 与装备尚未做确定性检查，只覆盖阵营、数量、时长和四类事件。
- 验收模型仍可能过度判断，已用规则约束，但没有关键词过滤或二次确认。
- 下一阶段重点：报错关键字→`errors-ref`/lesson 词法检索、静态引用检查（platform_type 先定义后使用）、按错误定向修复，而不是整份重生成。
- `架构.md` 由用户维护，本阶段未改，契约/事件/留痕部分以本文为准。
